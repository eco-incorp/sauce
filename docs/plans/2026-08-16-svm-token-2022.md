# SVM Token-2022 foundation (2026-08-16)

Branch: `feat/svm-token-2022`.

## Why

Every SVM venue adapter under `sdk/src/svm/venues/**` historically assumed each
mint is owned by the legacy SPL Token program
(`TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`). A mint can instead be owned by
Token-2022 (`TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb`) and carry extensions
that change the amount actually received (TransferFee), require extra accounts
(TransferHook), or make it un-routable (NonTransferable, PermanentDelegate, …).
Assuming legacy silently over-quotes (loses bps) or derives the wrong ATA (the
ATA seed includes the token program id).

This branch lands the SHARED, correctness-critical core every venue reuses:

- `sdk/src/svm/token-program.ts` — per-mint token-program resolver.
- `sdk/src/svm/token-extensions.ts` — TLV extension parser + exact fee math.
- `sdk/src/svm/venues/manifest/index.ts` — the anchor conversion (size heuristic
  → real resolver + graceful self-drop).
- Tests: `sdk/test/svm/token-program.test.ts`, `sdk/test/svm/token-extensions.test.ts`.

## Shared API

### `token-program.ts`

- `TOKEN_PROGRAM_ID`, `TOKEN_2022_PROGRAM_ID` — `@solana/kit` `Address` constants.
- `classifyMintProgram(mint, data): Address` — pure, from data shape.
- `resolveTokenProgram(load, mint): Promise<Address>` — reads the mint via the
  `AccountLoader` and classifies it. Throws if the account is missing.
- `resolveTokenProgramByOwner(mint, ownerOf): Promise<Address>` — escape hatch
  for the one ambiguous case (below), resolving strictly by owning program.
- `createTokenProgramResolver(load)` — a caching per-mint resolver
  (`Map<mintBase58, Address>`) so repeated resolves in one pool/route read once.
- `isToken2022Mint(data)`, `SPL_MINT_SIZE`, `T22_ACCOUNT_TYPE_OFFSET`,
  `T22_ACCOUNT_TYPE_MINT`, `T22_TLV_START` helpers/constants.

**Detection rule** (from data shape, since `AccountLoader` returns data only, not
the owner):

- exactly **82 bytes** → legacy classic SPL mint.
- **≥ 166 bytes** with the account-type byte at offset **165 == 1 (Mint)** →
  Token-2022 (82-byte base padded to 165, then the 1-byte account-type
  discriminator, then the TLV extension region).
- any other length/type byte → throws (not a mint layout).

**The one unresolvable case, documented not papered over:** a Token-2022 mint
with **no extensions** is also exactly 82 bytes, byte-identical to a legacy mint.
The data-only resolver classifies it as legacy — which is safe for routing (no
fee, no blocking extension → routes identically). When the true owner is needed
for an extensionless mint (e.g. picking the CPI `token_program` account), use
`resolveTokenProgramByOwner` with a lookup that can read the owning program (a
full `getAccountInfo`, not the data-only `AccountLoader`). This matches the
existing pumpswap/juplend-amm adapters' own documented assumption.

### `token-extensions.ts`

- `parseMintExtensions(mintData): { transferFee?, transferHook?, blocking: string[] }`
  — TLV walk. Returns `{ blocking: [] }` for a legacy 82-byte mint.
  - `transferFee?: TransferFeeConfig` — `{ olderTransferFee, newerTransferFee }`,
    each `TransferFee { epoch, maximumFee, transferFeeBasisPoints }`. Both
    schedules + their epochs are captured so a caller can pick the one effective
    at the current epoch.
  - `transferHook?: { programId, extraAccountMetaListPda? }` — non-nil hook
    program only. The `ExtraAccountMetaList` PDA
    (`["extra-account-metas", mint]` under the hook program) needs an async PDA
    derivation, so the sync parser leaves it undefined; the caller derives it.
  - `blocking: string[]` — reasons the mint is un-routable through a plain
    transfer: `NonTransferable`, `PermanentDelegate`, `ConfidentialTransferMint`,
    `MemoTransfer-required`, and `DefaultAccountState=frozen`.
- `getEpochFee(cfg, epoch): TransferFee` — newer if `epoch >= newer.epoch`, else older.
- `calcTransferFee(amount, cfg, epoch): bigint` — the exact fee.
- `netTransferAmount(amount, cfg, epoch): bigint` — `amount - fee`.

## Exact TLV / fee formula and authoritative source

**Mint TLV region** begins at byte **166**. Each entry is
`extension_type: u16 LE, length: u16 LE, value: [u8; length]`; `type == 0`
(Uninitialized) terminates the scan. All integers little-endian (spl-pod).

**TransferFeeConfig** (extension_type **1**, length **108**):

| offset | field | type |
| --- | --- | --- |
| +0 | transfer_fee_config_authority | Pubkey (32) |
| +32 | withdraw_withheld_authority | Pubkey (32) |
| +64 | withheld_amount | u64 LE (8) |
| +72 | older_transfer_fee | TransferFee (18) |
| +90 | newer_transfer_fee | TransferFee (18) |

`TransferFee` (18 bytes): `epoch: u64 LE (8)`, `maximum_fee: u64 LE (8)`,
`transfer_fee_basis_points: u16 LE (2)`.

**Fee** (spl-token-2022 `TransferFee::calculate_fee` /
`TransferFeeConfig::calculate_epoch_fee`):

```
bps  = get_epoch_fee(epoch).transfer_fee_basis_points   // newer if epoch >= newer.epoch else older
fee  = 0                                                  if bps == 0 or amount == 0
fee  = min(maximum_fee, ceil(amount * bps / 10_000))     otherwise
recipient receives amount - fee
```

`ONE_IN_BASIS_POINTS = 10_000`. Rounding is **ceiling** on the fee.

**Authoritative sources** (cross-checked via the solana-mcp docs corpus before
finalizing):

- Extension/TLV & account-type layout: spl-token-2022 `PodMint` /
  `PodStateWithExtensions`; confirmed by orca-so/whirlpools
  `MintWithTransferFeeConfigLayout` proptest fixture
  (`LEN = 82 + 83 + 1 + 2 + 2 + 108`; `account_type = 1`, `extension_type = 1`,
  `extension_length = 108`; `TransferFee` field order epoch, maximum_fee,
  basis_point).
- `TransferFeeConfig` struct + `calculate_epoch_fee`/`calculate_fee`:
  spl-token-2022 `extension/transfer_fee/mod.rs` (`older_transfer_fee` used if
  `epoch < newer.epoch`, else `newer_transfer_fee`; ceil-div, min with
  `maximum_fee`).

**How a venue uses it:** net the fee on BOTH legs so the netted quote matches
realized on-chain output — the input-side deposit into the pool vault
(`netTransferAmount(amountIn, feeIn, epoch)` if the INPUT mint is a fee mint),
and the output-side withdrawal from the vault to the user
(`netTransferAmount(grossOut, feeOut, epoch)` if the OUTPUT mint is a fee mint).
`epoch` must equal the cluster epoch the swap executes in.

## Graceful-degradation rule

When a mint is Token-2022 (and the venue's on-chain swap ix is Tokenkeg-only) or
carries any `blocking` extension, the venue **self-drops**: `fetchPoolConfig`
throws a clearly-described error. The SvmRoute orchestrator catches a
`fetchPoolConfig` throw and silently drops that venue candidate (the same path an
unsupported swap direction already uses). This is preferred over the old
size-based throw because the detection is now correct (real program + extension
check, not a fragile `length !== 82` heuristic that both mis-rejects extensionless
T22 and mis-accepts a bare-extension token account). **The legacy path stays
byte-identical**: a classic mint classifies as Tokenkeg, parses no extensions,
and the config is built unchanged.

For venues whose swap ix DOES accept a per-side `token_program` account (the
`swap_v2` shape), the eventual upgrade is to net the transfer fee in
`referenceQuote` and thread the resolved program per side, instead of dropping —
recovering the bps a drop would forgo.

## Anchor conversion (done): `manifest`

`fetchManifestConfig` previously threw `... is not a classic SPL mint (Swap is
Tokenkeg-only)` whenever `mintData.length !== 82`. Now, per mint: load bytes
(preserving the not-found message), `classifyMintProgram` → drop if Token-2022,
`parseMintExtensions` → drop if any `blocking` reason. Legacy mints build the
same config as before. This is the reference pattern for the per-venue work-list
below. Full T22 swap plumbing for manifest (optional mint accounts +
swap_v2-style ix) is a later per-venue task, out of scope here.
